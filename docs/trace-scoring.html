Grading a trace

A trace records one interaction. Its grade helps you find examples worth turning into regression tests, benchmarks and training data.

A grade can arrive after the reply

Lifty already links an applied proposal or an answered clarification to the original trainer trace. In this integration, the field is simply grade. Lifty can use the customer’s proposal decision as evidence for Pass or Fail.

  • Start the clock on selection. Lifty saves a durable deadline after the customer applies the proposal. At the deadline a job checks whether that selection has received a follow-up. Silence alone, without selection, earns no pass.
  • Keep the history. A linked complaint appends a new grade to the original trace. The list shows Fail. The inspector shows the earlier provisional Pass and the reason for the revision.
How does Lifty know which reply?
  1. When Lifty saves the reply, it stores the SDK trace reference in that assistant message’s metadata. For illustration, message m17 belongs to trace reply_42. Only Lifty needs the message ID.
  2. When the customer selects an option, Lifty’s existing confirmation request identifies the message. Its clarification flow also carries a question ID. The backend looks up the corresponding reply for the authenticated user.
  3. For a free-text complaint, add a reply-to link in Lifty. “Reply to this answer” on m17 saves the new message with replyTo = m17. The backend verifies ownership and conversation membership, then reads the saved trace ID. A plain chat message with no reliable target leaves the earlier grade alone.
  4. Only then classify the linked pair. “Wrong workout” can explain a Fail. “That workout was hard, thanks!” contains negative-sounding words without rejecting the reply. If the classifier is uncertain, record no new grade. The new message can have its own trace.

Inspect grade value


  • Booleans. For a boolean grade, true means Pass and false means Fail. The design preview also shows a single named boolean as its field and Yes/No, so timed_out: true reads correctly.
  • Labels and numbers. Use declared choices, show two chips plus an overflow count, and preserve zero and empty selections. Numeric grades display their stored value.
  • Other JSON. Show “View JSON” and open the authorized inspector. Bound the value size and depth, render escaped text, and put content-bearing fields under instance content-access and retention settings.
  • Missing evidence. Ungraded is distinct from false, zero, and an empty array. A trace can stay Ungraded indefinitely or enter a later review batch. Show the source beside a recorded grade.



Grade a trace with its ID and a value


Lifty can send Pass or Fail, or simply finish the trace. Calling grade() is optional. AutoEval shows Ungraded until someone records a grade.


1. Set up the SDK once on Lifty’s server


const autoeval = createTraceClient(trainerTraceConfig);


  • autoeval is the SDK client. It reads the instance address and app key from Lifty’s backend environment. One client can record many replies.
    • 

  • Every trace starts Ungraded. The default grade accepts true or false. For another shape, supply a grade definition at initialization. Lifty needs no custom name or rule declaration.


What is in trainerTraceConfig?

This is an ordinary object assembled by Lifty. The examples use the SDK’s existing field names.


FieldWhat it tells AutoEval


policyOptional for summary-only traces. The SDK supplies an empty schema when omitted. Lifty’s trainerPolicy declares which fields it sends, their types and which fields contain conversation or workout content.


experimentThe configuration that produced the answer, including the code revision, prompt, model and settings. In an offline evaluation it also identifies the dataset and run.


redactorVersionA redactor is Lifty’s code that removes or masks identifying details from selected content. For example, it replaces an email address with “[redacted]”. This field identifies the revision of that code. The current SDK requires it to send content.


The old createCaptureFromEnv name means “create a trace recorder using environment settings.” The createTraceClient entry point lets Lifty decide when to send data. Legacy clients keep their existing grant and withdrawal behavior.


2. Save the trace ID with the assistant’s reply


const trace = autoeval.begin();
const reply = await trainer.answer(prompt);
const savedReply = await messages.save({
  text: reply.text,
  traceId: trace.reference?.traceId
});
after(() => trace.end({
  content: { conversation: selectedMessages }
}));


trace is a recorder for this one request. begin() creates its ID locally. messages.save represents Lifty’s database write and returns the saved message. after schedules the SDK send after the customer receives the response. The real trainer stores the reference in message metadata. The selected conversation must match its declared schema.


3. Grade that same reply later


const target = await messages.findForUser(user, replyTo);
if (target?.traceId) {
  await autoeval.grade({
    traceId: target.traceId,
    value: false,
    reason: "Customer selected a different workout."
  });
}


messages and trainer stand for Lifty’s own storage and agent code. The later handler reloads the reply from storage. A missing or undelivered trace stays ungraded. reason is optional explanatory text. Lifty owns the implementation of its timer and classifier.


HTTP request, retries and late arrivals

POST /v2/traces/{traceId}/grades
{ "value": false, "reason": "Wrong workout." }


  • Only the value is required in the body. Optionally send occurredAt (Unix milliseconds) from the original business event. Use it for delayed jobs. Otherwise the first submission time applies.
  • The app key identifies Lifty. The server uses the trace ID in the path to find the grade definition saved at capture. It validates the value and stores the source, decision ID and event time. The client sends no policy version, grant, definition ID or sequence.
    • 

  • Pick the current decision by event time, breaking ties by server acceptance order. A delayed 60-second timer uses its deadline as event time and rechecks the linked reply before emitting. A late delivery cannot displace a later-dated complaint.
    • 

  • The SDK can reuse an idempotency key for the same submission. A durable job can use its stored event UUID in the optional Idempotency-Key header across process restarts. Identical replays return the original receipt. Reuse with different content returns 409. Unknown traces and wrong value shapes are rejected.
  • Reasons are optional diagnostic content. The server stores them only when the original trace has a redactor version, conversation content is enabled, and the content retention window is still open. Structured JSON uses its declared field’s category. Allow the client key to write only its own app’s grades.


Declare another grade shape
Keep the same grade call. Pass the definition as grade at initialization. Each example shows the shape-specific fields.
// One or several labels from a fixed vocabulary
{ kind: "category", choices: ["resolved", "partial"] }
{ kind: "multi_select", choices: ["resolved", "on_topic", "concise"] }

// A numeric grade
{ kind: "number" }

// JSON validated against a field in trainerTraceConfig.policy.content
{ kind: "json", contentField: "review" }
Multi-select accepts unique declared choices. For JSON, declare the field’s shape and category in the trace policy. The trace list shows “Structured JSON”. An admin can load the value in the trace inspector.




Which version changes?
Keep the agent version and the grade definition separate. Every trace identifies the agent that answered. A grade also identifies the definition used to grade it. You can then change the agent and measure it with the same yardstick.



  • First definition. Lifty starts with a boolean grade at v1. Each trace pins its grade shape. The server calculates a definition ID from the shape and version, so booleans and labels stay distinguishable even when both clients use the default version number.
  • Same shape, different meaning. If Pass changes from 60 to 120 seconds, Lifty declares grade: { kind: "boolean", version: 2 }. This gives the revised grading rule a new identity. No rule expression or evaluator hash is required.
  • Late feedback after a deployment. The old trace keeps v1. Save the rule version with Lifty’s delayed job and apply it when grading the reply, or leave it ungraded if the old rule is unavailable. The backend can validate the value’s type. Only the app can verify its private rule.


How the existing SDK calculates identity
A fingerprint is a hash, a short identifier calculated from the contents. Both SDK and server normalize the fields first. Resending the same declaration produces the same ID.

The client-grade implementation pins its definition to the trace. A future benchmark would freeze a grading rubric with the dataset. A changed grader need not create a new agent version. Shipping changed grading code in the same build can still change the existing experiment ID through its code revision.


Turn a graded trace into a reusable case
A production Fail tells you where to look. A reusable test also needs a prompt, enough starting context to replay it, and a way to recognize a good answer from any candidate agent.


  1. Observe. Lifty logged a run after the customer selected a bike workout. The linked complaint changed the trace grade to Fail. Preserve that decision, its source, definition and time as provenance.
    2. 

  2. Review and freeze. A reviewer creates a synthetic fixture with the bike plan selected, the prompt “Log my selection,” and a tool stub that returns the plan. Define the assertion “the proposed session uses the selected bike plan.” Freeze this case and rubric in a dataset version. Keep the complaint and expected answer out of candidate inputs.
    3. 

  3. Benchmark. Run Lifty before and after a prompt change, or run a second compatible agent through an adapter. Give each the same cases, starting state, tools and grading rubric. Compute fresh grades for their outputs. Report pass count, case count and missing grades. Failed or partial executions count as failures under the existing benchmark convention.
    4. 

  4. Train. For supervised fine-tuning, export the prompt, relevant tool context and a reviewer-approved correct assistant response. For preference tuning, pair a preferred correction with the rejected reply for the same input. A boolean grade alone supplies neither target. Reserve a held-out benchmark split and keep related conversations together to avoid leakage.


What the standardized Grade field buys us
Every graded trace can expose the same envelope: trace ID, definition ID and version, typed value, source and decision time. The UI renders that value. Dataset review selects a specific decision so later feedback cannot silently change a frozen case.


Two apps can both say “Pass” while measuring different things. Cross-system benchmarking uses one shared task and rubric. Within a report, aggregate matching definitions and sources. Complex JSON can support an assertion after a reviewer chooses a field or comparator.


A clean 60-second window is live customer feedback. Replaying a prompt cannot reproduce that customer’s reaction. Here the offline assertion tests the underlying workout-selection error. The same reviewed training examples can be exported for the operator’s model or a customer’s model in its required format.


AutoEval already has finalized datasets, evaluation runs and training workflows. Promoting a graded SDK trace into a portable case and exporting its reviewed labels are proposed connections between those workflows.


Grade a batch when you’re ready
Proposed batch workflow. Lifty can already send a trace and leave its grade blank. In the planned operator UI, filter the trace list to Ungraded, select the replies to review and choose how to grade them.

How the hosted judge runs
  1. Operator → AutoEval. Configure a backend secret such as OPENROUTER_API_KEY. Approve a profile for this app with a provider, model, prompt/rubric, output definition, permitted input fields, budget and timeout. Reuse AutoEval’s provider registry.
  2. SDK → ingest. Pin the requested profile version on new traces. Defaults to off. Resolve the immutable profile digest and report disabled, unapproved or unavailable settings separately from capture success.
  3. AutoEval → worker. Enqueue one durable job per trace/profile digest when an operator starts a batch or a new trace requests automatic judging. Check operator-approved data categories for this provider, retention and spend limit before dispatch. Send only approved redacted evidence. A missing key or required input skips the call.
  4. Worker → provider → AutoEval. Request schema-constrained output where supported and validate locally. Persist a separate judge grade with the profile digest, requested/resolved model when known and evaluation time. A timeout or malformed response yields a job error and an unknown grade.


Which grade appears in the list?
A batch grades the selected grade, such as grade v1. If the trace has no definition yet, the operator selects one when creating the batch. Display its saved value with Client, Judge or Human as the source. Keep every decision in the inspector. A separate rubric like reply-fit gets its own grade. If another reviewer or the client fills the grade while the batch is running, skip that trace at save time. An explicit regrade can append a revision later.
